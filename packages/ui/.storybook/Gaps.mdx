# Available UI and remaining work

<p className="ds-doc-lead">Which backlog items have reusable UI, and what still needs implementation in the product.</p>

Updated 7 September 2026. "Available" means package UI code with stories and tests. The corresponding GitHub issue, server flow or payment integration may still be incomplete.

## Available in the design system

| Layer | Delivered |
| --- | --- |
| Foundations | Semantic colors; Blue and Green in light/dark; Inter for UI and DM Mono for the wordmark/code; typography, spacing, radii, shadows, motion, icons and responsive rules |
| Actions and fields | Button, Input, Textarea, Label, Checkbox, RadioGroup, Switch, Select and FormField |
| Display and navigation | Card, Badge, Avatar, Separator, Tabs, Accordion, Breadcrumb and Pagination |
| Overlays | Dialog, AlertDialog, Popover, Tooltip and DropdownMenu with keyboard behavior |
| Feedback | Alert, Progress, Skeleton, LoadingMessage, ErrorMessage and EmptyState with recovery/action slots |
| Shared patterns | CrudForm validation, saving and right-aligned secondary/primary actions; DataTable labeling, pagination and horizontal scrolling; AppShell and full-width AuthLayout actions |
| Mentor feedback | Optional rating aggregates, written reviews and empty state, accessible review form, and technology chips with decorative icons |
| Handoff | Searchable component gallery, props and state examples, usage/accessibility guidance, contribution and change conventions |

Forms have unique field IDs, associated errors, root validation messages and required-field semantics. They prevent repeated submissions while saving. Tables put wide content in a named, keyboard-focusable scrolling region. Card titles support the heading level their page needs.

## Before using this in the product

1. Review the visual identity on real screens. The team needs to choose a default from the supported Blue and Green themes and assign design and engineering owners.
2. Connect each screen to the shared API layer. Stories use local data and MSW examples; the server must validate data, enforce permissions and handle business transitions.
3. Decide the Q18 conversation channel, Q19 payouts, Checkout hold/abandonment rules and answer-editing policy. The catalogue shows the relevant UI states, but these policies are still open.
4. Test authenticated flows with persisted data and review accessibility on every completed page. Unit coverage and sampled keyboard, contrast and responsive checks cover the library, not the full application.
5. Assign an owner, review token/API changes and record migration notes before wider use. External publication and synchronization require explicit approval.

Accessibility follow-up: the open Select popup needs a screen-reader review in its host page. Its browser keyboard scenario passes, but a standalone automated scan flags focusable content inside the hidden preview background. That finding remains documented for review.
