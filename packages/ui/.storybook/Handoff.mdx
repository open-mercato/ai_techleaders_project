# E01 and E02 implementation handoff

Use these finished screen compositions alongside the feature specification when
implementing accounts, roles and mentor onboarding. The prototype uses the same
`@devmentor/ui` components, tokens, fonts and icons as this Storybook. Its account,
save and provider responses are simulated locally. This handoff has 29 prototype
screens; the complete Storybook contains 288 stories and 60 documentation pages.

The UI/prototype contract is
`.ai/specs/2026-09-09-e02-design-handoff.md`. E01 also has the accounts-and-roles
specification at `.ai/specs/2026-09-04-accounts-and-roles.md`. The UI contract
covers all eight stories' visible flows. The E02 production contracts are also
in the repository: `.ai/specs/2026-09-08-mentors-become-bookable.md` and its five
story specifications. The prototype README links each specification. Use them
alongside these UI compositions for services, data, authorization and integrations.

## Implementation boundaries

- The screen composition, spacing, typography, action order and visible recovery
  copy form the UI handoff. Use the shared components instead of recreating their
  markup in application pages.
- Real OAuth, password hashing, verification and invitation email, tokens,
  cookies, persistence, authorization and provider webhooks belong to the
  application. Demo outcomes do not prove any of these mechanisms work.
- E02 acceptance adds mentor access to the current account. General registration
  gives mentee access; no screen can self-assign operator access.
- The same mentor data drives editing, public preview, prices and available
  times. Each confirmed booking keeps its price snapshot. The application must
  enforce these rules under concurrent requests too.
- Connect is designed here for iteration 1.1. The response preview asks for no
  real payout details and never contacts Stripe. Returning from a provider is
  not proof that payouts or a payment are enabled. Mentors manage their own setup
  on s28; operators read the Payout setup column on s25. Neither surface exposes
  bank or identity details, and public profiles show no payout status.
- Reviews and search are approved design extensions. Their production rules must
  be recorded in the accepted feature specification, since the original backlog
  still excludes them. Review storage, eligibility, moderation and search data
  access remain application work.

The reusable workflow lives at
`.agents/skills/devmentor-prototype/SKILL.md`. Invoke `$devmentor-prototype` when
extending these flows. It points to the current source, validation commands and
design rules. It does not publish changes or contact reviewers.

## Review before implementing

Walk E01 and E02 from their start links, then repeat the failure paths in their
state maps. Review light and dark themes, desktop and 320px mobile, keyboard
order, validation focus and retained values after failure. On compact workspace
screens, **Menu** opens the authorized navigation links. Existing comments
stay attached to stable screen IDs and can be exported from **Review tools**.

Use `npm run test:unit:coverage`, `npm run test:prototype`, the three typecheck
commands, lint and builds when changing the source. The prototype checks local
behavior. Production account and booking flows also require the repository's
integration tests with real application boundaries.
