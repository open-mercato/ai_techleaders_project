- 2026-09-15 — **A `CHECK` written with `between` can never match the schema, because PostgreSQL does not store `between`.** `SessionMessage` declared `length("body") between 1 and 4000`, the migration created exactly that, and the database was correct — but PostgreSQL rewrites `between` at parse time and hands the constraint back as `(length(body) >= 1) AND (length(body) <= 4000)`. MikroORM's comparator normalizes whitespace, quotes, casts and `in (…)`, but it does **not** rewrite `between`, so the two strings never compare equal and `getUpdateSchemaSQL()` reported a permanent, self-perpetuating drift: a drop-and-re-add of a constraint that was already right. `migrations/devmentor.json` had recorded the two-comparison form all along, which is where to look first when the drift diff is a no-op. Writing the check as two comparisons in the entity, the migration and their tests removes the drift without changing what the database enforces. Generalisation: **the entity's expression string is compared against what the database says, not against what you wrote**, so any SQL sugar the server desugars — `between`, `not in`, `x = any(…)` spellings, an unparenthesised boolean, a bare `now()` default — belongs in the stored form. The repo's other checks (`"price_25_cents" > 0`, `cardinality("roles") >= 1`) are all already written that way; copy one rather than inventing a spelling.

- 2026-09-15 — **`findByText` is satisfied by the commit, and focus arrives after it — so a focus assertion placed straight after an `await findBy*` is a race, not an assertion.** `MentorProfileEditor.test.tsx` submitted a form, awaited the server-side field error's text, then asserted `document.activeElement` synchronously. React renders that text during the commit; `CrudForm` moves focus from a `useEffect`, which React flushes *after* the commit. `waitFor`'s MutationObserver fires the moment the text node lands, so the test's next line can — and roughly one run in ten does — execute before the passive effect has run at all. It failed in CI on an unrelated PR while passing on every local run, which is the signature of this bug: the assertion is about a state a *later* task produces, so whether it holds depends on how the runner happened to interleave the queues that run. The fix is `await waitFor(() => expect(document.activeElement).toBe(group))`; the two other async focus assertions in this repo (`mentor-prices-client`, `mentor-profile-client`) already did exactly that. Two generalisations. (1) **Only a synchronous `fireEvent` justifies a synchronous focus assertion** — `act` flushes effects before that call returns, so the sibling tests that assert focus after client-side zod validation are correct as written; every assertion downstream of an `await` needs `waitFor`. (2) More broadly, anything a component does in `useEffect` — focus, scroll, a measurement, an analytics call — is *not* proven by the DOM change that triggered it, and a test that treats the two as simultaneous will fail on the CI machine rather than yours.

- 2026-09-14 — **A test double selected by a *missing* credential is a production payment bypass waiting for an ordinary deploy.** `selectPaymentGateway` returned `MockPaymentGateway` whenever `STRIPE_SECRET_KEY` was absent, which reads as a safe default and is not one. `assertProductionSecrets` gates `SESSION_SECRET` and `MAIL_API_KEY` but not the Stripe key, so the ordinary shape of a first deploy — session secret and mail key set, newest variable not yet added — booted green on the mock; `MockPaymentGateway.createCheckoutSession` returns the caller's own `successUrl`, so pressing **Pay** landed on the success page having paid nothing, and `MOCK_WEBHOOK_SECRET` is a constant in this repository, so anybody could sign a `checkout.session.completed` and confirm their own booking. The argument that let it through — "a mock takes no money, so the failure mode is a product that visibly cannot be paid" — is false twice over: the mock *does* return a usable success URL, and "cannot take money" is not a safe failure at the one route whose entire purpose is taking money. This repo already had the rule, twice, on `selectGithubIdentity` and `selectMailer`: **selection is from flags that are present, never from credentials that are absent, and one flag is never enough to select a fake.** `config/env.ts` even *documented* the correct behaviour beside the keys while the container did the inverse — so the generalisations are (1) a new test-double seam copies the two-signal rule from the existing seams rather than re-deriving whether it needs one, and (2) when a comment and the code it sits next to disagree about a security property, that is a bug report, not a stale comment.

- 2026-09-14 — **A mock adapter that accepts every input cannot tell you the real API would reject it, and the gap is widest exactly where the real API has a documented constraint.** Stripe refuses a Checkout Session whose `expires_at` is under 30 minutes away. `BOOKING_HOLD_MINUTES` is exactly 30 and the hold starts when the slot is *reserved* — a whole HTTP round trip before checkout is *started*, because the panel calls `POST /api/bookings` and then `POST /api/bookings/:id/checkout` — so every request asked for an expiry a few hundred milliseconds inside the floor and would have come back `invalid_request_error`. **Every real payment would have failed, and 2176 unit tests plus 82 integration tests were green**, because `MockPaymentGateway` accepts any expiry and no test contacted Stripe. The clamp belongs in the adapter, where the translation to the provider's constraints already lives, not in the service. Generalisations: (1) when a port's contract carries a value the *provider* constrains — a minimum expiry, a maximum page size, an id format, an enum of currencies — the mock should enforce that constraint too, or the mock is not a stand-in but a different API; (2) a limitation honestly recorded as "owed to manual QA" is a statement that a class of defect is currently undetectable, so the review that goes looking for that class is the highest-value review you can run on the branch.

- 2026-09-14 — **A migration test that says "roll back one" quietly starts testing a different migration the moment anything lands after it.** `migrations.integration.test.ts` proved mentor prices were independently revertable by calling `migration:down` with no target — correct while `mentor_prices` was the newest migration, and silently wrong once E03 added five after it: the rollback reverted `payout-held-notification` instead, the price columns were still there, and the *next* test ("matches the complete entity model") failed with a schema-drift diff that pointed at the notification CHECK rather than at the test that had moved the schema. The fix is to name the target (`migration:down --to <migration>`) and then migrate all the way back up, so the test asserts what it means and leaves the schema where the next test expects it. Generalisation: **a test whose setup depends on being last is a test with an expiry date.** Anything that says "the previous one", "the latest", or "one step back" about an ordered, append-only sequence — migrations, event logs, seed batches — should name the element instead, and the failure it produces when it goes stale will usually surface in a neighbouring test rather than in itself.

- 2026-09-14 — **`agent-browser` sessions attached to one CDP endpoint share that browser's cookie jar; sessions that launch their own Chrome do not.** On a machine that cannot start the bundled Chrome (missing system libraries, no `sudo`, and a `DevToolsActivePort` error that says nothing about either), `AGENT_BROWSER_CDP` pointing at `chromedp/headless-shell` in a container is a working substitute — but every scenario file then inherits whatever cookies the last one left, and `TC-AUTH-004`'s "…and no session cookie" assertion starts failing against `devmentor_session=expired.session.value` for a reason that has nothing to do with the product. `tests/integration/agent-browser.ts` clears cookies on the first attach per session, which restores per-file isolation while keeping the within-file jar a persona switch needs. Generalisation: when a test harness swaps process isolation for a shared connection, the state that *was* isolated by the process is now the harness's problem to reset, and the symptom will be an unrelated assertion in an unrelated file.

- 2026-09-11 — **On `/mentor/profile`, a readiness label and a publish refusal use the same text.** The `ReadinessChecklist` always renders each unmet requirement (e.g. "Choose at least one technology.") as an `h3`, and a refused publish renders that same label again as the field error. `agent-browser wait --text` therefore passes before the publish request returns. Wait for `[role="alert"]` instead: only `CrudForm` field and form errors carry that role on this page. See `TC-MENTOR-PROFILE-001`.

- 2026-09-10 — **Removing a macOS launchd job that starts `npm run dev` does not guarantee Next's child process is gone.** The orphan keeps `.next/dev/lock`, while a generated QA launcher can start a replacement job, record its transient PID and publish a dead URL. A forced bootstrap must always tear down the recorded descriptor, then remove stale same-worktree launchd jobs and terminate their validated process groups before starting Next. Scope stale-job cleanup by the exact project root embedded in `launchctl print`; never kill every `devmentor-qa-*` job across worktrees.

- 2026-09-10 — **Commit every non-sensitive `.ai` artifact with the work that produced it.** Run logs, QA reports/screenshots, generated test-environment helpers, PR drafts, working references and previews are repository records, not disposable session material. This supersedes the former `AGENTS.md` rule that kept session materials local.

- 2026-09-10 — **`instanceof` is not a reliable test for an `AppError`, because Next evaluates `@devmentor/core` once per module graph while `getContainer()` shares one container through `globalThis`.** A page renders in the SSR/RSC graph and a Route Handler runs in its own; each gets its own copy of `http/errors.ts`, and therefore its own `AppError` *class object*. That is invisible until a value crosses — which the container makes routine, because whichever graph builds it first owns every service in it. So `UserService.authenticateWithPassword` (constructed in the SSR graph, because a page resolved the container first) threw an SSR-graph `UnauthorizedError` at `/api/auth/login`, whose `apiHandler` compared it against the *route* graph's class. `isAppError` answered `false`, a deliberate `401 unauthorized` was logged and served as `500 internal_error`, and a `429` lost its `Retry-After` entirely. **The reproduction is order-dependent, which is why nothing caught it**: restart, `POST /api/auth/login` first → 401 (the route graph built the container); restart, `GET /sign-in` first → 500. Unit tests never see it at all, because a single test process evaluates the module once. The fix is a brand looked up in the cross-realm registry — `Symbol.for('devmentor.http.app-error')` on `AppError`, checked by `isAppError` — which is the same problem `entities/define.ts` solves for entity schemas with a `globalThis` singleton, in the shape that suits a class. Three generalisations. (1) **No code may narrow one of these with `instanceof`**; discriminate on `code`, which is a string and crosses intact (`sign-in-redirect.ts` matched `instanceof ConflictError` and was silently sending users with a genuine email conflict to `?error=unavailable`). (2) The same applies to any cross-graph identity check — `Symbol.for`, a string tag, or a `globalThis` singleton, never a class or a module-local symbol. (3) A 100%-covered error path proves the mapping, not that the value reaching it is the one the mapping recognises; the check that finds this class of bug is a request against the running app, made in both orders.

- 2026-09-10 — Three things the rate limiter's `INSERT … ON CONFLICT` upsert (B8) got wrong before it got them right, all only visible against a real PostgreSQL. (1) **A data-modifying CTE that deletes a row the main `INSERT … ON CONFLICT DO UPDATE` then lands on is not allowed** — same command, same row, and PostgreSQL refuses it rather than picking an order. The pruning `DELETE` of expired rows therefore carries `and "key" <> ?`, excluding the key being charged; nothing is lost, because that key's expired row is reset to `1` by the rollover `CASE` anyway, which is the same outcome the delete would have produced. A CTE prune that filters only on age looks correct and blows up exactly when a bucket has been idle longer than the longest window, i.e. rarely and in production. (2) **`em.execute` returns a `timestamptz` as a *string*, not a `Date`** (`'2026-09-10 09:58:20.015+00'` — note the space, so it is not ISO-8601 either). MikroORM installs its own `pg` type parsers and hands raw SQL results back unmapped and un-camel-cased, so `returning "window_start"` needs parsing and `returning "count"` does not (`int4` arrives as a `number`). The fix that avoids the question entirely: compute the derived value in SQL and cast it — `greatest(1, ceil(extract(epoch from "window_start" - ?) + ?))::int` — so the driver hands back an `int4` and no date parsing exists to get wrong. Column names come back **snake_case**; there is no automatic mapping on `em.execute`. (3) **The window rollover has to be inside the same statement as the increment.** "Read the row, decide whether the window expired, then write" reopens the exact gap the upsert closes: two attempts arriving at an expired window would each reset the count to `1` instead of `1` then `2`. As a `CASE` in the `DO UPDATE` it is evaluated under the row lock, and 8–12 genuinely concurrent connections produce 8–12 distinct counts with no lost update (verified both ways against PostgreSQL 17). The generalisation: **a check-then-act on a counter is only atomic if the check is an expression inside the writing statement**, and the only way to know is to run it on real concurrent connections — a unit test with a fake `EntityManager` proves the module's decisions and nothing about the SQL's.

- 2026-09-10 — **A credential inside a URL's query string is invisible to pino's `redact`, because redaction matches key *names* and a query parameter is not a key.** `apiHandler`'s catch block logged `{ err: error, path: req.url }`, and `req.url` in a Route Handler is the **full** URL. `logger.ts` redacts `password`/`passwordHash`/`token`/`authorization`/`cookie` at three depths, so `{ token }` and `{ err: { token } }` are censored — but `path: "…/api/auth/github/callback?code=<live GitHub authorization code>&state=<signed state token>"` is one ordinary string value, and no path expression can reach inside it. Every unexpected failure on that route wrote live credentials to stdout at `error` level, and the same shape applies to `/api/auth/verify-email?token=…`. **Redaction is not a safety net for URLs; strip the query at the call site.** `packages/core/src/http/safe-url.ts` is now the one place that rule lives: `withoutQuery` (keeps scheme/host/path — `outbound.ts` needs the host to say *which* integration failed) and `requestPath` (path only, non-throwing because it runs inside a catch block where a second throw would replace a clean 500 with an unhandled rejection). Three generalisations. (1) Any value a log line carries that is a *composed string* — a URL, a `Location` header, a `redirect_uri`, an interpolated error message — is outside redaction's reach by construction; only structured fields are protected. (2) The route-level `try/catch` does not save you, because the leak is in the *wrapper*: `apiHandler` sees whatever escapes, including a throw from `getEnv()` on line 51 of the callback route, which sits deliberately outside the route's own `try`. (3) The audit that finds these looks for `req.url`, `new URL(`, `searchParams` and interpolated `Error` messages, not for logger calls — `sign-in-redirect.ts` logs a **constant** `route` and is the pattern to copy.

- 2026-09-10 — **MikroORM v7 merges environment variables *under* file config, so any `MIKRO_ORM_*` override of something `config.ts` states explicitly is silently inert.** `MikroORM`'s constructor does `options = options.preferEnvVars ? Utils.merge(options, env) : Utils.merge(env, options)` (`node_modules/@mikro-orm/core/MikroORM.js`), and `preferEnvVars` is unset here — so file config is the *source*, not the *default*. Verified empirically against the installed 7.1.14: with both variables exported, `orm.config.get('migrations')` still reports `snapshot: true, snapshotName: 'devmentor'`; strip those two keys out of `createOrmConfig()`'s output and the same run reports `false` / `.snapshot-devmentor`. This corrects the 2026-09-09 entry below, which prescribed `MIKRO_ORM_MIGRATIONS_SNAPSHOT=false` for throwaway-database tests: `tests/integration/migrations.integration.test.ts` had been setting exactly that since it was written, and it does **not** work — that suite rolls the schema backwards, so `migration:down` re-stored `packages/db/migrations/devmentor.json` from the rolled-back database and dirtied a committed file. The toggle has to be an input to `config.ts` itself, hence `DB_MIGRATIONS_SNAPSHOT` in `packages/db/src/env.ts`. The general rule: **before trusting a `MIKRO_ORM_*` variable, check whether the config file pins that same key** — and never flip `preferEnvVars` to "fix" one variable, because it promotes *every* MikroORM variable above the zod-validated config, including the connection ones. (The orphaned `.snapshot-devmentor.json` this repo carried is now deleted; `devmentor.json` is the only snapshot.)

- 2026-09-10 — **`next-env.d.ts` must be git-ignored, not committed in either of its two forms.** `next dev` writes `import "./.next/dev/types/routes.d.ts"`; `next build` rewrites the same lines to `./.next/types/...` (`node_modules/next/dist/lib/typescript/writeAppTypeDeclarations.js` composes the path from `distDir`). Whichever form is tracked, the *other* mode dirties a tracked file — so committing the production form to keep CI's Build job clean just moves the dirt onto every developer's dev server, and vice versa. Next 16's own documentation is unambiguous: *"Add it to `.gitignore`. If your project already tracks the file, remove it from Git."* (`node_modules/next/dist/docs/01-app/03-api-reference/05-config/02-typescript.md`). Nothing breaks: verified that `tsc --noEmit` passes with the file absent **and** `.next/` absent, because `skipLibCheck` means the unresolved `./.next/...` imports inside a `.d.ts` are never reported and no source here imports a non-code asset needing `next/image-types/global`; CI regenerates it during `npm run build` anyway. Keep the entry in both tsconfig `include` arrays, as those same docs require. Note this does **not** contradict `packages/app/AGENTS.md`, which says to commit the agent-instruction block `next dev` re-adds *to that file*: that block's generated content is stable, so committing it converges; `next-env.d.ts`'s content alternates, so committing it cannot.

- 2026-09-10 — **A test double that redirects the browser must return an origin-*relative* URL.** `MockGithubIdentityAdapter.authorizeUrl` built its callback as `new URL(GITHUB_CALLBACK_PATH, env.APP_URL)`, so the start route's `Location` was the absolute `http://localhost:3000/api/auth/github/callback?...`. Reached on any other origin — `127.0.0.1` rather than `localhost`, a preview hostname, a tunnel, the integration harness's ephemeral port — that redirect **moves the browser to a different origin mid-flow**, and the `devmentor_oauth_state` cookie the same response just set (`Path=/; HttpOnly; SameSite=Lax`, bound to the origin the browser was actually on) is therefore not sent to the callback. The callback compares `?state` against a cookie that is simply absent, correctly refuses, and the user lands on `/sign-in?error=state` — *"that sign-in request could not be verified"*. The damage is that the symptom names the CSRF defence while the cause is a configuration value silently rewriting the origin; nothing logs, nothing 500s, and the state check is doing exactly its job. Two rules. (1) **`APP_URL` answers "what is this deployment's canonical public origin", never "where is my own callback".** A component that is *the same application* has no business naming an origin: return `/api/auth/github/callback?...` and let RFC 7231 §7.1.2 resolve it against wherever the browser already is (verified: Next 16 passes a relative `Location` through byte-for-byte). The *real* adapter is the genuine exception and must stay absolute, because GitHub matches `redirect_uri` against the OAuth app's registered absolute URL — so both adapters now carry a test pinning their respective shape, and the fake's constructor dependency on `env` is gone entirely along with its only reason to exist. (2) **Any absolute self-URL is a latent cookie bug.** If a flow sets a cookie and then redirects, assert the redirect is origin-free rather than trusting that the configured origin is the one in the address bar; a unit test that only parses the result with `new URL(value)` cannot tell the two apart, because `new URL` of a relative string throws rather than reporting the difference.

- 2026-09-10 — **Adding an optional parameter to a cradle-injected factory turns the cradle into that argument.** `container.ts` registers `logger: asFunction(createLogger)` in an `InjectionMode.PROXY` container, and PROXY mode means awilix calls *every* `asFunction` factory with the **cradle proxy as its first argument** — a bare function reference does not "take no arguments", it takes whatever its signature declares. So when `createLogger` grew an optional `destination?: DestinationStream` (a test seam, so a test could read the emitted line back), the cradle was handed to pino as a stream; `pino.js` does `if (typeof stream.emit === 'function')`, the proxy turned that property read into a resolution, and **every request that built the container died with `AwilixResolutionError: Could not resolve 'emit'`** (path `eventBus -> logger -> emit`) — sign-in, the role homes, `/admin`, every API route, all 500. Two rules follow. (1) An `asFunction` factory either destructures the cradle in a *required* parameter (`({ orm }: Cradle) => orm.em.fork()` — the intended pattern) or takes **none**; never an optional one. If a factory needs a non-cradle argument, give it a separate, differently named function that no registration references (`createLoggerTo(destination)`) and pin the registration's arity with an explicit arrow, `asFunction(() => createLogger())` — that arrow is load-bearing, not noise. (2) **The suite was green throughout, and that is the real lesson**: `container.test.ts` does `vi.mock('../logger', …)`, so nothing anywhere resolved the *real* factory through a *real* container, and `logger.test.ts` called `createLogger(destination)` directly, never through one. A composition-root test that stubs the thing being composed proves only that awilix can return a stub. Every mocked edge of the container needs at least one test that leaves it real — `container.logger.test.ts` is that test for the logger, and `vi.mock` being module-wide is why it has to be its own file. 100%-per-file coverage does not see this class of bug at all: the wiring line was "covered" by the stubbed run.

- 2026-09-10 — Two traps met while landing the first guarded pages and the signed-in integration scenarios. (1) **A Next route group's parentheses must be escaped in a glob, or `coverage.include` silently measures nothing.** `'packages/app/src/app/(auth)/sign-in/page.tsx'` in `vitest.config.mts` is a *pattern*, and tinyglobby/picomatch read `(auth)` as a group matching the directory `auth` — the entry matches zero files, the page drops out of the report, and the 100%-per-file gate passes because it never looked. Write `'packages/app/src/app/\\(auth\\)/sign-in/page.tsx'` (verified: unescaped returns `[]`, escaped returns the file). Check a new page actually appears in `coverage/unit/coverage-final.json` rather than trusting a green run. (2) **The integration harness built its child environment before it chose the app's port**, so `APP_URL` stayed at its `http://localhost:3000` default while the app listened on an ephemeral one. Nothing noticed until a route needed the app's own address: `MockGithubIdentityAdapter.authorizeUrl` resolves the OAuth callback against `APP_URL`, so a harness sign-in would have bounced to port 3000 and never come back. `tests/integration/global-setup.ts` now reserves the port *before* `integrationChildEnvironment(databaseUrl, baseUrl)`, and the parameter is required so the default cannot be reintroduced by omission. Any config a child process needs about *itself* has this shape — decide it before the environment is built, not after.

- 2026-09-10 — Four traps met while building the F3 page guards and the F4 `WorkflowAction`. (1) **Next 16 gives a Server Component no way to ask for its own pathname**, so a page guard cannot build `?returnTo=<current>` by itself: `headers()` exposes only the incoming HTTP headers, `usePathname` is documented as "a **Client Component** hook", and `nextUrl.pathname` belongs to `NextRequest`, which only a Route Handler or the proxy holds. The alternatives are a proxy stamping a header on every request or passing the literal each page already knows — `requirePageSession(currentPath)` / `requirePageRole(role, currentPath)` take it as a parameter. (2) **jsdom's `window.location` members are `[LegacyUnforgeable]`**, so `vi.spyOn(window.location, 'assign')` dies with `TypeError: Cannot redefine property: assign`; `vi.stubGlobal('location', { assign })` plus `vi.unstubAllGlobals()` works, and so does `Object.defineProperty(window, 'location', { configurable: true, value })`. (3) **An `eslint-disable-next-line` whose justification runs onto further `//` lines disables the wrong line** — each `//` is its own comment, so the directive applies to the continuation comment and the real violation is still reported. Flat config's default `reportUnusedDisableDirectives` catches it as a warning; put the prose *above* the directive and keep the directive on the line touching the code. (4) **`eslint-config-next`'s rules apply to every package, not just `app`** — `@next/next/no-location-assign-relative-destination` fires inside `packages/ui`, where `useRouter` cannot even be imported. The sign-out hard navigation carries an explicit disable for exactly that reason.

- 2026-09-09 — **A MikroORM `UniqueConstraintViolationException` still carries the `pg` error's `constraint` name, but only because `DriverException`'s constructor copies every own property off the original** (`node_modules/@mikro-orm/core/exceptions.js`: `Object.getOwnPropertyNames(previous).forEach(k => this[k] = previous[k])`). Nothing in the exported `.d.ts` declares `constraint`, so it must be read through a narrowing cast. This is load-bearing for every B10 check-then-act recovery (seven more are named in the backlog): "some unique constraint blew up" is not a recoverable signal — `mentor_profiles_user_id_unique` is a bug, `users_email_unique` is a lost race — so the recovery must match the *name* and rethrow anything it cannot attribute, including a wrapper with no `constraint` at all. Two more traps in the same shape: retry the whole matching order rather than only the lookup that failed (the winner may now be visible to an earlier branch), retry exactly once (two consecutive losses are a defect, not contention), and pass `{ clear: true }` to `em.transactional` so the retry does not inherit the losing attempt's unit of work — the entity it failed to insert is still queued in it and would lose the same race for ever. Defer event emission until after the commit for the same reason: a rolled-back attempt must not have announced `auth.user.created` for a row that does not exist.

- 2026-09-09 — **The MikroORM migration snapshot this repo actually uses is untracked, and the tracked one is orphaned.** `migrations.snapshotName: 'devmentor'` in `packages/db/src/config.ts` makes the Migrator read and write `packages/db/migrations/devmentor.json` (the file name is `${snapshotName}.json`), but the file committed at bootstrap is `packages/db/migrations/.snapshot-devmentor.json` — the *default* name (`.snapshot-<dbName>`) from before `snapshotName` was set. Nothing reads the tracked one any more, so it still describes the pre-`auth-identity` `users` table, and a fresh clone has no snapshot at all: `db:migration:create` then silently diffs against whatever database is connected instead of against the committed schema. Commit `devmentor.json` with every migration that regenerates it. Two related traps: `migration:up`/`:down` also rewrite the snapshot from introspection when it differs (`Migrator.runMigrations`), which is why `tests/integration/environment.ts` sets `MIKRO_ORM_MIGRATIONS_SNAPSHOT_NAME` — but it points at the *tracked* `.snapshot-devmentor`, so an integration run dirties a committed file; a throwaway-database test should set `MIKRO_ORM_MIGRATIONS_SNAPSHOT=false` instead and write nothing.

- 2026-09-09 — Two traps met while building out the app env schema (`packages/core/src/config/env.ts`). (1) **`z.string().url()` accepts `localhost:3000`.** Zod v4 delegates to `new URL()`, which happily parses that as the scheme `localhost:` with path `3000`, so a plain `.url()` on `APP_URL` waves through a value missing its `http://` and only fails much later, as an OAuth redirect URI GitHub rejects. Pin the scheme: `z.string().url({ protocol: /^https?$/ })`. The same applies to any URL var whose scheme is not free (`DATABASE_URL` is the exception — it is genuinely `postgres:`). (2) **`NodeJS.ProcessEnv` is globally augmented by Next to make `NODE_ENV` required**, so `getEnv({})` — the "an empty environment still parses" case that guards the CI Build job — does not typecheck even though it is exactly what the schema is for. Vitest does not typecheck, so this only surfaces in `npm run typecheck`. Cast once in the test helper to `Record<string, string | undefined>` rather than sprinkling `NODE_ENV` through fixtures that are meant to be empty. - 2026-09-10 — **Storybook and esbuild treat any ancestor `.pnp.cjs` as Yarn Plug'n'Play configuration, even inside a nested npm project.** The symptom is valid Storybook imports failing with “The Yarn Plug'n'Play manifest forbids importing” after `npm ci`, while CI passes on a machine without the unrelated manifest. - 2026-09-08 — Three traps found while specifying E02 (`.ai/specs/2026-09-08-mentors-become-bookable.md`) that bite anyone touching roles, slots, or a MikroORM relation before its table exists. (1) **`grantRole` bumps `session_version`, so granting a role signs the caller out unless the route re-issues the cookie.** E01 puts `grantRole` on the closed list of `session_version` triggers; invitation acceptance (#15) is the first grant path, and a handler that commits the transaction without signing a fresh cookie leaves the user's own action invalidating their token — the redirect to `/mentor` then lands on sign-in. Only a route handler can set a cookie in the App Router, so this can never be fixed in a page or a service. (2) **A slot is a bare start instant but the *mentee* picks 25 or 50 minutes at booking (#17 + #21), so slots at 14:00 and 14:30 can double-book a mentor** — neither issue notices. The read-time filter is `viableLengths(slotStart, occupied, lengths)`; the guarantee is *not* a per-slot lock, which two concurrent bookings on two different slots sail straight through. Serialise on the **mentor** row (`SELECT … FOR UPDATE` on `mentor_profiles`) and back it with `EXCLUDE USING gist (mentor_profile_id WITH =, tstzrange(starts_at, ends_at) WITH &&)` on `bookings`. (3) **Never declare a MikroORM relation whose column does not exist yet.** A `Slot.booking` property with no `booking_id` column puts the column in every generated `SELECT` (so all reads of `slots` fail) and regenerates it on the next `db:migration:create` diff against the committed snapshot. Also note two boundaries that block the obvious implementation: `packages/db/**` may not import `@devmentor/core` (`eslint.config.mjs:44-48`), so a migration cannot call a vocabulary's `sqlValueList()` or a `uniqueSlug()` helper — hand-write the SQL and guard the drift with a `core`-side test that reads the migration file; and `SDLC.md:97` grades **any** schema migration `risk-high`, however small the feature.

- 2026-09-08 — **A "required in production" env check must not live in the zod schema.** `npm run build` forces `NODE_ENV=production`, the CI Build job sets no env at all, and `getEnv()` is reachable at build time from `admin/page.tsx` and the pino logger — so a schema refine that fails on a *missing* `SESSION_SECRET` in production would break every CI build. - 2026-09-04 — Four constraints found while specifying E01 (`.ai/specs/2026-09-04-accounts-and-roles.md`) that will bite anyone adding UI, a scoped list, or admin chrome. - 2026-09-04 — An OAuth **state** cookie must be `SameSite=Lax`, never `Strict`. The engineering-standards spec suggests "`lax` (or `strict` for auth-only routes)", and `Strict` looks like the safer read for an auth cookie — but the provider's callback is a cross-site top-level navigation, so a `Strict` cookie is not sent and *every* sign-in fails state validation.
